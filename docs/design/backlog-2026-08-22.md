## §D. The R1·10b ordering derivation — run before filing any row that depends on it

**The standing sentence:** *"stage 2's `EndCombatWithOutcome` prefix closes the only route R1·10b
uses, and the `bypassOnce` hatch that would re-open it ships in that same PR"* — used to justify
"R1 before W2". Read literally it contains its own refutation: closed and re-opened in one commit
means not closed.

**What R1·10b measures:** on the CLIENT, does the debriefing open after a forced combat end —
`pbj.debrief-probe` `present=`/`entered=` before/after. It decides M12d stage D0's Shape A vs B.

**The two routes, derived from code (all read this session):**

- Pre-W2 route: `cm.force-victory` → `CombatStateCheck()` (= `IDUtility.IsGameState("combat")`) →
  `ScenarioUtility.EndCombatWithOutcome(CombatOutcome.Victory, early: true)`
  (`decompiled/PhantomBrigade.DebugConsole/ConsoleCommandsCombat.cs`, member `ForceVictory`,
  `:71-79`).
- Post-W2 route: `pbj.force-end victory` → `IsGameState("combat")` guard → sets
  `WreckingPatches.BypassCombatEndOnce = true` → **the identical call**
  `ScenarioUtility.EndCombatWithOutcome(resolved, early: true)` → clears the flag in a `finally`
  (branch `DestructProbeGlue.cs`, member `ForceEnd`, `:694-742`). The prefix's predicate
  short-circuits on `BypassCombatEndOnce` (branch `WreckingPatches.cs`, member `SuppressCombatEnd`)
  and the call is synchronous, so the whole vanilla body runs inside the bypass window.
  `SuppressCascade` deliberately ignores the bypass — and the wreck cascades are not on the
  debriefing-entry chain (`ReplaceCombatResolved` → overworld transition →
  `OverworldCombatOutcomeProcessingSystem`), so that difference cannot move the reading.

**Candidate justifications, adjudicated:**

1. *Argument difference between the routes* — **NONE.** Same static method, same arguments, same
   game-state precondition. FAILS.
2. *Hatch is client-only* — the command runs anywhere `IsGameState("combat")` holds; on a host it
   reports `prefix was NOT ARMED` and still ends combat. R1·10b is a client reading anyway. FAILS.
3. *Hatch is unverified* — **REAL, and it is the only survivor.** The command's registration is
   verified statically (`Add(nameof(ForceEnd), "pbj.force-end", typeof(string))` in
   `RegisterConsoleCommands` — the `[Command]` attribute registers nothing in this game, and this
   is the explicit `TryAddCommand` path), and its output names its branch (`BYPASSED` / `NOT ARMED`
   / `NOT IN COMBAT` / `BAD ARGUMENT` / `THREW` — a silent return is impossible by construction).
   But it has never run in a game, the whole branch has never run a test, and it lives in the
   uncovered project. A route you have never driven is a risk you schedule around, **and that is
   intent, which rots** — so it is written here as exactly that.

**Verdict: "R1 must precede W2" is NOT a structural constraint.** It is a choice between:

- **Option 1 — measure first (the standing user ruling).** Take R1·10b on today's `main` (0.23.0)
  via `cm.force-victory` before W2 merges. Cost: one extra two-instance sitting before the W2
  deploy (or a split R1: R1a pre-W2 without readings 6a–6f, R1b post-W2 with them — resolving R-3's
  contradiction by splitting the run). Benefit: the route is vanilla shipped code, zero instrument
  risk; and the measurement environment (no stage-2 flags on the client) is the one M12d's D0 was
  originally specified against.
- **Option 2 — merge first, one run.** Gate + merge `dad9a50`, deploy 0.24.0, run ONE full R1 in
  which R1·6a (`pbj.wreck-patches`) is taken first, and R1·10b is taken via `pbj.force-end`.
  Cost: R1·10b rides an instrument that has never fired; if `pbj.force-end` fails at the rig, the
