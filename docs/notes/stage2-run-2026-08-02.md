# Stage 2, verified — two real game instances over a WAN (2026-08-02)

The first session in which two separate installations of Phantom Brigade, on two machines in
different households, executed a shared combat turn. This is the milestone M8 was gated on.

## What it establishes

- **Two independent games agreed on post-turn state.** The client diverged before correction —
  expected, since it never simulates — then hard-set to the host's snapshot and *independently
  recomputed* the same digest: `DIVERGED | host dc7fab21 | local 8711cb08` followed by
  `corrected | 19 units | digest dc7fab21 OK`.
- **M6 keyframes reached a real client for the first time.** 12 tracks, 588 keys over a 5-second
  window — about 49 keys per track against the ~51 predicted for 0.1 s sampling plus the appended
  final key. Units slid along their real paths in an idle pose, which is correct for M6: the root
  transform moves and nothing drives the animator.
- **The lobby-then-load ordering works.** The client was welcomed at `turn -1`, sat in Lobby, and
  moved to Planning only when the host entered combat last and broadcast `CombatStart`. That path
  had been derived from the code and never run.
- **Loading a save inside a live session does not break it.** Both sides logged `combat restored`
  mid-session and the connection survived.
- **Ownership enforcement holds between two real games.** The players deliberately both ordered the
  same unit; the host rejected the one that did not own it.
- **M9's offer/decline path ran.** The host offered the scenario and the client declined, having
  already digested its own copy to the same `1c7cd3f5` — cross-platform agreement between Proton and
  Windows. The byte *transfer* did not run and remains proven only by the loopback selftest.

## What it exposed

16 of the client's 18 submitted orders were rejected. Only 3 were the deliberate ownership test; the
other 13 were the **enemy AI's own planned actions**, which a client holds in its local ECS without
the `AIAction` tag the bridge filters on. Fixed afterwards by narrowing the Ready batch to
`OwnedUnits` in `ClientSession` — see `NetLog.OrdersNotOurs`.

Also visible: 19 units in the snapshot against 12 keyframe tracks. Consistent with the documented
limitation that `CombatReplayHelper.units` is seeded from the `OnExecutionStart` roster, so a
later-spawning wave has no track. The session did not run long enough to trigger that wave, so
nobody saw those units pop into place.

## Redaction

These are the `[pb-and-j]` lines only, lifted from the two `Player.log` captures. Everything else
was dropped rather than edited, which matters: the tester's Windows account name appears **only** on
game-engine lines and never on a mod line, so it is absent here structurally rather than because
someone spotted every occurrence.

Substituted within the kept lines: both public IP addresses (`<host-ip>`, `<peer-ip>`), both machine
names (`host-pc`, `peer-pc`), the peer's ephemeral source port (`<port>`), and the session id
(`<session>`). The raw logs were destroyed and `logs/` is now gitignored.
